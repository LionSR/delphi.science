# Curated work groups (local proposal)

Delphi retains records as `<source>/<key>`. `site/lib/records/work-groups.ts` adds a read projection for one reviewed research work, with exact member IDs, a stable canonical main record, and evidence URLs. No title matching, storage merge, write redirection, new tables, or migration is involved. Removing the curated entry reverses the projection without changing either source's history.

## Reviewed membership

- **Canonical main record:** `lean/anthropics__formal-math__eth`: the official Anthropic paper and Lean proof repository. Its source date, 2026-08-06, is repository creation, **not** this paper's publication date. The adapter's README fallback explains the repository-shaped metadata.
- **Alternative source:** `hexagon/2610.00577`: paper, *A 2^o(n) Time Algorithm for 3-SAT* by Claude (Anthropic). Its source date is paper publication, 2026-10-27.

Evidence: [repository README](https://github.com/anthropics/formal-math/blob/main/eth/README.md) explicitly names the paper and accompanying Lean 4 formalization; [Hexagon paper](https://hexagonmath.org/2610.00577v1) has the matching title, authorship, abstract and contribution. The evidence-backed work display title is `A 2^{o(n)} Time Algorithm for 3-SAT`: it preserves the exponent that the README parser currently flattens in the raw source title. The raw title remains unchanged in the source snapshot and source view. This is curated work identity across distinct manifestations, not an assertion that files are identical or that Lean checked the paper's exact claim. The separate OpenAI ETH result is not a member. No similar-title heuristic is used.

Read-only source snapshots on 2026-11-05 had 10 and 6 discussion URLs; all 6 Hexagon URLs overlapped Lean. Both had zero votes/comments/reviews/mentions. Production snapshots are only for local QA; current data is computed at read time.

## Search, filters, totals and ranking

1. Apply the entire query to each source row independently. A conjunction must match one row; `source:hexagon is:formalized` cannot borrow Lean's assertion. This includes `NOT`, `OR`, exact `id:`, text, date and source filters.
2. An indexed preflight over curated member IDs uses the requested sort to choose the highest-ranked **matching** source per work. Exclude other matching members in the normal SQL query **before** its count, limit and offset. This retains the existing optimized hot/cold ranking queries; no fetching a page and then dropping duplicates. Nonmembers take the existing path.
3. `work.main_record_id` is always `lean/anthropics__formal-math__eth`, independent of filtering/ranking; the Hexagon paper is explicitly an alternative source. Grouped cards, work titles, main links, citation metadata, JSON-LD and detail-page canonical links use the official main record whenever available. The result's root ID, URL, title, source metadata, counters and self link remain the selected matching **source view**, explicitly identified by `work.view_record_id`; they do not choose the canonical main work. `work` explicitly adds reviewed membership and all currently available source snapshots (even members that did not satisfy the query), as context. Exact-ID/source queries can therefore select either original identity. Detail GET always retains the requested identity, including `/id/` upstream redirects. There is no destructive redirect; both original pages and write targets remain accessible. If the main record is absent, its main ID is retained, the UI labels it unavailable, and title links fall back to the available source rather than a 404. No alternative is silently promoted to main.
4. `total`, `count`, numbered pages and cursors describe grouped results. Source inventory badges still count raw source records; a work can contribute to multiple source inventories. Cursors retain the existing cached-total/live-read contract, not snapshot isolation.
5. Rank is the best matching individual source under the requested sort, **never the sum** of scores, reactions, mentions or shared discussion. With newest/oldest/published filters, existing source dates remain searchable and sortable; a repository-only match still uses repository creation. The UI labels that meaning explicitly. It does not manufacture a work publication date by taking the earliest member date. The main choice is independent of publication metadata: citation date and PDF use the available Hexagon paper, and are omitted if that member is absent; the repository creation date is never used as the work's publication date.
6. Day/week/month, score, mentions and responded likewise keep source ranking semantics. The union of work responses is for display, not a new popularity metric. A work with disjoint responses spread across sources may rank below one whose single source has more responses. This conservative boundary avoids inventing an aggregate interaction policy.
7. Keyword/vector ties now include ID for deterministic source selection and paging. Hybrid search retains its existing 200 keyword + 200 vector candidate cap and pre-existing all-match count semantics. Its ranking preflight applies the member restriction after global candidate ranking, so RRF is not computed over only the group. A separate complete matching-member read keeps grouped totals correct even when neither member reaches the candidate window; members outside that window use ordinary relevance/date order only to choose which non-retrieved member to exclude. Hybrid counts may exceed the candidate window, as before. This change does not redesign hybrid retrieval.

## Interactions and source assertions

Votes, reactions, review/comment threads, mentions, ownership rules, old comment anchors, write endpoints and source history stay bound to the original record ID. A person may have interacted with both IDs; no cross-source unique-person or score total is invented. Grouped cards expose per-source interaction links/counts rather than a global vote button. Either detail URL offers its existing vote/comment actions with an explicit source-ID notice and links to the other source. The source panel labels main versus alternative, and retains differing titles, authors, abstracts, formalized/verified assertions, reception summaries, dates and original URLs. Full source metadata remains reachable through each source JSON endpoint. Grouping confers no verification status.

Full API results add `work.sources[].record` snapshots and `work.discussion`; existing root `discussion` and `discussed` remain source-specific for compatibility. Compact results include compact snapshots and the union response count, omit the union payload, and retain explicit false formalized/verified/withdrawn assertions within sources. The OpenAPI and MCP output contracts include `work`; their root IDs and interactions remain unchanged. MCP's existing root response/latest-response fields remain source-specific; the work union is available under `work` (full results).

## External-response identity and provenance

`work.discussion` is a union by normalized URL, not by title or excerpt. Normalization uses URL host/default-port canonicalization, removes `utm_*`, `fbclid`, `gclid`, sorts query parameters, and unifies Twitter/X status URLs by numeric post ID (ignoring status-link share parameters). Fragments (which can identify different answers/comments), other schemes, path case, meaningful query values, trailing slashes and different hosts remain distinct deliberately; semantic redirects are not guessed. Consequently, different section-anchor URLs can remain separate even if they happen to describe one article; conflating different responses is avoided.

Each union item retains all original `{record_id, link}` assertions, including repeats within one source and conflicting dates, stances, attribution or excerpts. Display fields use the first available source in curated order (official repository then paper); provenance disclosures show the source assertions individually. A first-source stance is not presented as group consensus. The work count uses only distinct URL keys; it does not add the raw source counts. Raw source metadata and response arrays are untouched.

Absent members are not fabricated: a surviving record remains discoverable and its group contains only available sources. An absent exact ID still returns 404. No interactions are moved from an absent member.

## Verification and intentional boundaries

The dedicated PGlite integration suite covers filters and exact IDs, all 10 sorts, count/page/cursor consistency, repeated and shared URL links, conflicting assertions and dates, absent members, a separate similar-title OpenAI result, separate interactions by one human on both IDs, keyword/vector ranking, REST/MCP schema compatibility and unchanged upstream redirects. See the local verification report for final commands, results and browser screenshots.

This curated list is intentionally small. Its preflight is bounded by the search page-size maximum (currently 100 member IDs); a larger catalog would need a dedicated grouping query rather than growing this mechanism unchecked. Live production query latency and concurrent source-removal behavior have not been load-tested. The preflight, result and enrichment reads can observe concurrent edits, like existing live counts/paging; no snapshot isolation is promised.
